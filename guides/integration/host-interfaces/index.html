INTEGRATION/HOST INTERFACES

Host interfaces

The vehicle adapter answers these questions for you on a vehicle. Use the interfaces when you have no adapter, or when your game has a host of its own. Your own vehicle walks through the adapter and a complete wheel host, and Core concepts has the summary table. This page covers each interface in turn: what it is asked, what it answers by default, and how to implement it.

Who answers, and in what order

Section titled “Who answers, and in what order”

A component asks its owner through the host it finds, in this order:

  1. The explicit host, set with SetCrushformHost before BeginPlay. C++ only.
  2. The object registered for the owner in UCFHostRegistry, a world subsystem. Its Register, Unregister and FindHost are C++ only.
  3. The owner itself, when its class implements the interface.
  4. No host. The component then answers as a body with no host.

Your own vehicle gives the same order in one paragraph.

The vehicle adapter registers itself as the host of the five interfaces it implements: ICFDeformHost, ICFWheelHost, ICFBreakerHost, ICFTireHost and ICFEngineHost. A vehicle with an adapter needs no host of its own for them. ICFTireViewer is not implemented by the adapter. It belongs to the pawn that the player sits in.

A host that does not implement the interface is refused with an error, which is described in the Troubleshooting section at the end of this page. A second host for the same actor and interface replaces the first, with a warning.

Register a host with the registry

Section titled “Register a host with the registry”

Registering a host for an actor in the registry lets every component of that actor find it, without a SetCrushformHost call. The registry is a world subsystem, so reach it through the world. In the actor’s BeginPlay, register the actor itself as its wheel host, and remove the registration in EndPlay:

  • Unregister removes the entry only while it still holds that host.
  • Registering the same host again changes nothing and logs nothing.
  • FindHost also works without the registry. It then answers with the actor itself, when the actor implements the interface.

The answers you return

Section titled “The answers you return”

Every answer is an ECFHostAnswer:

ValueMeaning
DefaultDecide as the component does with no host.
YesYes.
NoNo.

An event you leave untouched in Blueprint returns the same answer as no host. An ECFHostAnswer event returns Default. An event that returns a list gathers nothing. GatherCrushformIgnoredActors returns false, which keeps the owner’s attached actors ignored.

Do not call an interface event by name on an interface pointer. Your own vehicle shows the Execute_ call to use instead.

ICFWheelHost

Section titled “ICFWheelHost”

The dirt layer of the body, UCFRollingAudioComponent and UCFRollingFXComponent ask it. A Blueprint host is asked once a frame, and every caller of that frame shares its answer. The event fills one FCFWheelContact for each wheel, on the ground or not:

  • WheelIndex must stay the same for a wheel from frame to frame.
  • A wheel in the air keeps bGrounded false. Its Point and PhysicalMaterial are not read.
  • A host that reports only the wheels on the ground is correct, but then no wheel is ever seen to leave the ground.

With no host the list is empty, and the body never gets dirty.

Blueprint. Add the interface in Class Settings > Implemented Interfaces > Add, then implement GatherCrushformWheelContacts in My Blueprint. It has an output array, so it is a function. The graph below implements it, prints when it runs, and leaves the array empty. Fill the array in your own graph.

ICFTireHost

Section titled “ICFTireHost”

UCFTireComponent asks it for the wheels of a vehicle, and writes the tyre offsets and pushes back to it. The host keeps no tyre state. The component remembers what it changed and gives every offset back when it goes away. There are four events:

EventAnswersDefault
GatherCrushformTireWheelsArray of FCFTireWheelDesc: the wheel’s mesh, its PhysicsRadius, its HostIndex, its VisualOffset and bAcceptsPushNothing, which keeps the tyres round
SetCrushformTireWheelOffsetsReceives the offsets the component changed, in one call: each OffsetCm and each PushCmNothing
GatherCrushformTireLoadRatiosContact force over nominal load, by HostIndex. An empty array means no force modelEmpty
GatherCrushformTireRigThe actors coupled with this one, itself includedJust this actor

Blueprint. Add the interface and implement the gather events as functions. The graph below implements GatherCrushformTireWheels. It prints when the event runs, and it leaves the array empty.

C++. The two gathers on a vehicle:

The push. A wheel with bAcceptsPush set is moved by its PushCm when its rim would otherwise enter an obstacle, so the tyre dents around the obstacle instead of the rim. Set bAcceptsPush only when SetCrushformTireWheelOffsets applies PushCm to the wheel mesh in the same call, in the owner’s space, and the mesh keeps that push until the next call. A host that ignores the push makes the push run up to the profile’s MaxPush. A host that lets it go stale, because something else moves the mesh or turns its parent against the owner, puts the dent off its place. The rim radius comes from the RimRadius parameter of the tyre material, or from the profile’s RimRadiusOverride; a wheel with neither is never pushed.

The adapter. UCFVehicleAdapterComponent applies the push itself and reports bAcceptsPush for its wheels until a Blueprint overrides SetCrushformTireWheelOffsets. A Blueprint that overrides it places the wheels itself and gets no push. A C++ subclass that overrides SetCrushformTireWheelOffsets_Implementation has the same duty as any host: call the base, which applies PushCm, or apply the push yourself, or override BuildTireWheels to report bAcceptsPush as false. The base converts the push to the wheel’s parent space once, when it arrives. A subclass whose wheel’s parent turns against the owner, such as a steering knuckle, or whose game rewrites the wheel’s relative location, no longer carries the push the tyre subtracts, so it reports bAcceptsPush as false.

ICFEngineHost

UCFEngineAudioComponent asks it once a frame for the engine. Its answer is an FCFEngineState:

Interfaces that are C++ only

Section titled “Interfaces that are C++ only”

ICFBreakableHost and ICFBreakableUnitPart are declared with CannotImplementInterfaceInBlueprint. Implement them in C++ only. They belong to breakable debris, and the members of both are listed in the API reference.

Check that it works

Section titled “Check that it works”
  • In a non-Shipping build, run Crushform.Debug 1 and hit the body with Crushform.DebugImpact. Damaged nodes appear where the body dented, which means the deform host answered.
  • Run Play In Editor and look at the Output Log for the error of a refused host and the warning of a replaced one. A clean log means each host was accepted.
  • With the wheel host implemented and the surfaces set up, drive through a mud strip. Dirt collects on the wheels and the body.

Troubleshooting

Section titled “Troubleshooting”

The host is refused, and the log names the interface

Section titled “The host is refused, and the log names the interface”

Cause. The object does not implement the interface, so the registry refuses it. The log says:

Fix. In Blueprint, add the interface in Class Settings > Implemented Interfaces > Add. In C++, add the interface to the class’s base list and override the events.

The wheels get no dirt

Section titled “The wheels get no dirt”

Cause. Either the wheel host gathers no wheels, or the project has no surfaces asset. With no surfaces asset, no body gets dirty. A host whose gather event is not implemented returns an empty list, which is the default.

Fix. Implement GatherCrushformWheelContacts so that it adds one FCFWheelContact for each wheel. Set Surfaces in Project Settings > Plugins > Crushform.

A call to an interface event fails in the editor

Section titled “A call to an interface event fails in the editor”

Cause. The event was called by name on an interface pointer, whose generated body is a check.

Fix. Call it through Execute_, as Your own vehicle shows, or use a message node in Blueprint.
